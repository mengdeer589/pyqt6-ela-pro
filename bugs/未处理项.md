## #10-B 非主屏最大化时 isFullScreen() 误报 → 标题栏拖拽失效（ElaAppBar NCHITTEST 闸门）

**状态**：未处理。**触发条件属 Win7 + Qt 5.15 环境**（本机 Win10/Qt 6.8.4 未复现）；表现层闸门代码属实。

**原文出处**：`full (3).md`（末尾疑似截断；原件已删，git `b56bd1e` 可查）

### 报告内容

**PyQt6 复测（2026-10-16）**：复现——probes/probe_fullscreen_state.py：副屏最大化后无边 QWidget isFullScreen=True 且 isMaximized=False（比原记录更重——原记录仅 isFullScreen 误报、isMaximized 仍 True），ElaWindow 副屏 isMaximized=True isFullScreen=True；主屏两者均正确。probe_maximize_discriminate.py：副屏最大化后 maximize 按钮位仍回 HTZOOM（库 NCHITTEST handler 在跑），标题栏 y=12 x 扫描全 HTCLIENT（主屏同扫描为 HTCAPTION）——caption 分支仍被误报中断，副屏最大化后标题栏拖不动。

**库 / 组件**：根因在 Qt 5.15 Win7 平台插件的 fullscreen 状态推断（无 Qt 源码现场，机制为推断）；表现层 PyQt5ElaWidgets C++ ElaAppBar::takeOverNativeEvent 的 WM_NCHITTEST（ElaWidgets/ElaAppBar.cpp ~L644）。

**现象**：窗口（无边框 / 自绘边框）在无任务栏的副屏上最大化后，标题栏（appbar）命中测试整条返回 HTCLIENT（而非 HTCAPTION）→ 最大化状态下从标题栏拖不动窗口（Windows 原生语义本应是「还原 + 拖动」）。主屏（带任务栏）最大化正常。非最大化状态两屏均正常。

**根因链**（2026-10-12 本机实测，Win7 SP1，双 1920×1080 并排，任务栏仅主屏底部；探针 probes/probe_fullscreen_state.py / probes/probe_maximize_drag2.py / probes/probe_maximize_discriminate.py）：

1. QWindow::isFullScreen() 误报：三方对照（最大化后续状态）——原生边框 QWidget 副屏 isFullScreen=False √；Qt::FramelessWindowHint QWidget 副屏 isFullScreen=True；ElaWindow 副屏 isFullScreen=True x；三者主屏均 False √（isMaximized() 两屏正确为 True）。
2. 机制（推断）：主屏底部 40px 任务栏使最大化窗口高 1040 ≠ 屏高 1080；副屏无任务栏，无边框窗最大化后恰好铺满副屏完整几何（(1920,0,1920×1080)）→ 平台插件把「无边框 + 恰好铺满整屏」推断为 fullscreen（Qt 的 showFullScreen 在 Win 上正是这样实现几何的），该推断不区分窗口实际处于 maximized 原生状态。
3. 表现：ElaAppBar.cpp NCHITTEST 的 caption 闸门 if (d->_containsCursorToItem(this) && !window()->isFullScreen()) → 误报的 isFullScreen 直接掐断整条标题栏。判别证据：副屏最大化后标题栏 x 扫描 (y=12) 全 HTCLIENT（主屏同扫描 HTCAPTION），而 maximize 按钮位置仍返回 HTZOOM (=9) ——库 handler 在跑，只有 caption 分支被掐；Qt 侧几何无偏移（appbar mapToGlobal 正确。QCursor::pos() 与 appbar 矩形包含关系实测为真）。

**期望行为**：

- Qt 侧：窗口处于原生 maximized 状态时 isFullScreen() 必须为 False（fullscreen 状态只应反映显式 showFullScreen() 请求）。
- 库侧（表现层）：NCHITTEST caption 闸门改为 !isFullScreen() || isMaximized()（或自行跟踪「用户是否显式请求全屏」）——最大化时标题栏按 Windows 语义应给 HTCAPTION，支持还原 + 拖动。

### 我方核实结论（2026-10-16，Win10 / Qt 6.8.4，双屏）

**代码证据**（`ElaAppBar.cpp`）：`:644` `if (d->_containsCursorToItem(this) && !window()->isFullScreen())` → `HTCAPTION`；否则落到 `:649` `HTCLIENT`。**只要 `isFullScreen()` 误报为真，整条标题栏命中确实会失效** —— 报告描述与代码一致。
（另注：`_containsCursorToItem` 判的是 `QCursor::pos()`（`ElaAppBarPrivate.cpp:232`），不是消息坐标。）

**运行时探针**：

- 副屏最大化后：裸无边 QWidget `isFullScreen()=False`、ElaWindow `isFullScreen()=False` —— **无误报**；
- 把真实光标移到标题栏后发 `WM_NCHITTEST`：副屏普通 / 副屏最大化 / 主屏最大化（对照）均返回 **HTCAPTION**（可拖动），无报告中的「整条 HTCLIENT」。

**未复现原因**：本机两块屏**都带任务栏**（`availableGeometry` ≠ `geometry`），报告触发条件是「无任务栏副屏 + 无边窗恰好铺满 → Qt 5.15 平台插件误判 fullscreen」，属 Win7 + Qt 5.15 环境。

**下一步**：需要「Win7 + 无任务栏副屏」环境复测；若成立，落点＝ `ElaAppBar` NCHITTEST caption 闸门（上游 C++，改法见上「期望行为」）。

## #15 PySide6/Qt6（Win7）：进程内出现过 CJK shaping 后，其后纯 Latin 文本渲染慢 20~40x（app 级 shaping 毒化）

**状态**：未处理。**属 Qt / DirectWrite 字体引擎层，与库无关**（报告自述「纯 QTextBrowser 即复现」）；本机 Win10/Qt 6.8.4 未复现。

**原文出处**：`full (8).md` + `full (9).md`（已删，git `b56bd1e` 可查原件）

> 注：原始片段个别数字存在波浪号导出损伤（如 `2040×`/`123127ms`/`恒1415ms`/`恒定6768`），本文件按上下文还原为 `20~40×` / `123~127ms` / `14~15ms` / `67~68`。

### 报告内容

**PyQt6 复测（2026-10-16）**：复现——probes/md_scroll_perf5.py 两序各独立进程：cjk_first 68.0 / 238.0 / 127.5 / 14.0 ms/step（viewer+CJK / viewer+ASCII / 原生+ASCII / 原生+CJK），ascii_first 6.2 / 67.4 / 233.3 / 128.5——纯 Latin 从 6.2 放大到 ~233（×38），原生 browser 同样毒化（128），CJK 自身两序恒定 67~68。与原记录（71.3/223.7/123.3/14.6 与 6.2/71.4/229.5/127.0）同量级。Qt 6.8.2 未见改善。

**库 / 组件**：PySide6 6.8.3 / Qt 6.8 DirectWrite 字体 shaping（Win7 SP1）。纯 QTextBrowser + setDocument 即复现，与 ela 无关（新建 QTextBrowser / 新建 QTextDocument 实例都无法摆脱 → app 级状态，推断在字体引擎/shaping 缓存层）。

**现象**：同一进程内只要渲染过 CJK 文本，其后一切纯 Latin 文档的滚动 paint 成本放大 20~40×；纯 ASCII 文档（13K 字符、约 100 折行）**123~127ms/帧**（原生 QTextBrowser，~8fps）；全新进程（无 CJK 历史）同文档 6ms/帧（160fps）。CJK 渲染本身不受历史影响（恒 14~15ms/帧原生口径）。两种顺序均复现且数值稳定：

- CJK 先行：viewer+CJK 71.3 → viewer+ASCII 223.7 → 原生新 browser+ASCII 123.3 → 原生+CJK 14.6；
- ASCII 先行：viewer+ASCII 6.2 → viewer+CJK 71.4 → viewer+ASCII（再次）229.5 → 原生+ASCII 127.0。

**复现**（2026-10-15，`uv run python probes/md_scroll_perf5.py cjk_first` 与 `... ascii_first`；离屏 1000×700、40px/步；probes/md_scroll_perf4.py m2~m6 为同型状态矩阵）。

**期望行为**：CJK 与 Latin 的 shaping / 字形缓存相互独立，任一脚本的渲染历史不应劣化另一脚本的后续渲染（至少不跨脚本毒化）。

**项目侧临时规避与移除条件**：无规避（项目约定）。影响面：以 CJK 为主的文档不受显性影响（CJK 自身不劣化，实测原生 15ms/帧含 234 个行内码 token）；受影响的是纯英文 / 纯 Latin 文档——宿主进程只要已渲染过 CJK（如宿主应用自身 UI 文案），其后打开纯 Latin 文档即 20× 变慢。注意与 #14 独立：#15 在原生 browser 上同样存在（123ms），viewer 无关；两者叠加时（viewer + 英文文档 + CJK 历史）实测 230ms/帧。Qt 侧修复（或可解释机制并给缓解）后关闭本条。

| 场景 | 本机实测 | 报告 |
| --- | --- | --- |
| ASCII（渲染 CJK 之前，新实例 ×2） | 3.6 / 3.6 ms | 6.2 ms |
