## #15 PySide6/Qt6（Win7）：进程内出现过 CJK shaping 后，其后纯 Latin 文本渲染慢 20~40x（app 级 shaping 毒化）

**状态**：Qt 层未处理（**属 Qt / DirectWrite 字体引擎层**，报告自述「纯 QTextBrowser 即复现」；本机 Win10/Qt 6.8.4 未复现）。**库侧可控触发点已于 2026-10-19 全部收口**（见文末更新）。

**原文出处**：`full (8).md` + `full (9).md`（已删，git `b56bd1e` 可查原件）

> 注：原始片段个别数字存在波浪号导出损伤（如 `2040×`/`123127ms`/`恒1415ms`/`恒定6768`），本文件按上下文还原为 `20~40×` / `123~127ms` / `14~15ms` / `67~68`。

### 报告内容

**PyQt6 复测（2026-10-16）**：复现——probes/md_scroll_perf5.py 两序各独立进程：cjk_first 68.0 / 238.0 / 127.5 / 14.0 ms/step（viewer+CJK / viewer+ASCII / 原生+ASCII / 原生+CJK），ascii_first 6.2 / 67.4 / 233.3 / 128.5——纯 Latin 从 6.2 放大到 ~233（×38），原生 browser 同样毒化（128），CJK 自身两序恒定 67~68。与原记录（71.3/223.7/123.3/14.6 与 6.2/71.4/229.5/127.0）同量级。Qt 6.8.2 未见改善。

**库 / 组件**：PySide6 6.8.3 / Qt 6.8 DirectWrite 字体 shaping（Win7 SP1）。纯 QTextBrowser + setDocument 即复现，与 ela 无关（新建 QTextBrowser / 新建 QTextDocument 实例都无法摆脱 → app 级状态，推断在字体引擎/shaping 缓存层）。

**现象**：同一进程内只要渲染过 CJK 文本，其后一切纯 Latin 文档的滚动 paint 成本放大 20~40×；纯 ASCII 文档（13K 字符、约 100 折行）**123~127ms/帧**（原生 QTextBrowser，~8fps）；全新进程（无 CJK 历史）同文档 6ms/帧（160fps）。CJK 渲染本身不受历史影响（恒 14~15ms/帧原生口径）。两种顺序均复现且数值稳定：

- CJK 先行：viewer+CJK 71.3 → viewer+ASCII 223.7 → 原生新 browser+ASCII 123.3 → 原生+CJK 14.6；
- ASCII 先行：viewer+ASCII 6.2 → viewer+CJK 71.4 → viewer+ASCII（再次）229.5 → 原生+ASCII 127.0。

**复现**（2026-10-15，`uv run python probes/md_scroll_perf5.py cjk_first` 与 `... ascii_first`；离屏 1000×700、40px/步；probes/md_scroll_perf4.py m2~m6 为同型状态矩阵）。

**期望行为**：CJK 与 Latin 的 shaping / 字形缓存相互独立，任一脚本的渲染历史不应劣化另一脚本的后续渲染（至少不跨脚本毒化）。

**项目侧临时规避与移除条件**：无规避（项目约定）。影响面：以 CJK 为主的文档不受显性影响（CJK 自身不劣化，实测原生 15ms/帧含 234 个行内码 token）；受影响的是纯英文 / 纯 Latin 文档——宿主进程只要已渲染过 CJK（如宿主应用自身 UI 文案），其后打开纯 Latin 文档即 20× 变慢。注意与 #14 独立：#15 在原生 browser 上同样存在（123ms），viewer 无关；两者叠加时（viewer + 英文文档 + CJK 历史）实测 230ms/帧。Qt 侧修复（或可解释机制并给缓解）后关闭本条。

### 我方核实结论（2026-10-16，Win10 / Qt 6.8.4）

**运行时探针**（纯 QTextBrowser，在屏 1000×690，测完销毁逐个新建实例）：

| 场景 | 本机实测 | 报告 |
| --- | --- | --- |
| ASCII（渲染 CJK 之前，新实例 ×2） | 3.6 / 3.6 ms | 6.2 ms |
| CJK 文档自身 | 5.1 ms | 67~71 ms |
| ASCII（渲染 CJK 之后，新实例 ×2） | 3.8 / 3.7 ms（×1.1 / ×1.0） | 229.5 ms（×38） |

本机未复现「跨脚本毒化」。该现象报告自己也注明「纯 QTextBrowser 即复现、与 ela 无关」，属 Qt/DirectWrite 字体引擎层，本仓库无需处理。

**下一步**：若 Win7 交付线上仍成立，向 Qt 侧反馈（附报告探针 `probes/md_scroll_perf5.py`）；库侧无落点。

### 2026-10-19 更新（下游 `下游项目反馈bug.md` §2/§3）：库侧触发点已收口

新一轮报告把慢路径的触发条件收敛为两条可操作的结论：**① 主字体缺对应字形
（逐字形 fallback）；② 多族字体列表本身（逐字形族匹配，与各族是否 CJK 无关）**
—— 库内两个已实测的触发点（终端默认 Consolas、查看器代码字符格式的
`[code font, "Microsoft YaHei UI", "Microsoft YaHei"]`）与随后**按同一机制审计
出的其余多族使用点**均已收口：

- `ElaTerminalView` 默认字体：中文系统改**单族** `Microsoft YaHei`
  （`terminal_view._default_font_families()`；非中文系统仍 `Consolas`）；
- `ElaMarkdownViewer` 代码字符格式：中文系统收成单族
  （`_code_format_families()`；默认代码字体 `_default_code_font_family()`
  在中文系统直接取 CJK 字体、不扫全量字体族）；
- 图表 `chartFont`：中文系统单族（`FONT_FAMILIES` 首族；其余族原就是
  mac / linux 字体，Windows 上从不生效）；
- chat `mono_font`（耗时 / 工具详情 / 差异）与消息头部标题：中文系统单族雅黑
  （标签可能含 CJK，单族 CJK 字体是唯一全免触发的选择，代价是丢等宽观感）；
- 探测统一走 `_internal.system_cjk_font_family()`（进程级缓存；仅「中文系统 +
  YaHei 可用」时启用，其它系统行为不变）；
- **例外**：`math_lite._font` 刻意保留多族（数学字形与 `\text{中文}` 覆盖
  二选一，且公式只渲染一次成图；见其 docstring）。

守卫：`tests/ela_terminal/test_terminal_font_policy.py`、
`tests/ela_markdown_viewer/test_md_cjk_fonts.py`、
`tests/ela_chart_widget/test_chart_font_cjk.py`、
`tests/ela_chat/test_chat_cjk_fonts.py`、
`tests/_internal/test_system_cjk_font.py`。

> 注：图表 / chat 两处是**审计推断**的同类触发点（其绘制路径 md 未实测；
> 小标签单次 fallback 是否也触发毒化未经 Win7 验证），按「同一机制、低代价」
> 原则先收口；若下游 Win7 实测有出入，以实测为准回改。

本机（Win10）复测**无慢路径现象**（Consolas / YaHei / 多族均 ~1.5–3ms/全幅重绘），

### 2026-10-21 更新（bug #20）：「CJK 主字体缺符号」方向 + 库自产标记

下游 Win7 实测把触发条件补成**三个方向**：① 非 CJK 主字体渲染 CJK；② 多族字体
列表；③ **CJK 主字体缺文本里的符号字形**（LLM 输出常带 ↔ / ⇒ / □ / √ 等，
雅黑 cmap 覆盖不全）。方向 ③ 同样走逐字形 fallback 并进程级毒化。

库侧自产进 `QTextDocument` 的缺字标记已全部换掉（本机 Win11 雅黑 cmap 用
`QRawFont` 复核：旧字形缺失、新字形存在）：

- 任务列表：`☐`/`☑`（U+2610/U+2611）→ `□`/`■`（U+25A1/U+25A0）；
- `<details>` / 推理折叠 + 超长代码折叠：`▸`/`▾`（U+25B8/U+25BE）→ `+`/`−`
  （U+002B/U+2212）；
- 示例终端：`✓`（U+2713）/`▸` 同样会被 QPlainTextEdit 的文档渲染 → 改为
  `√`（U+221A）/`+`。

`_internal.system_cjk_font_family()` docstring 与 `docs/performance.md` 已补上
方向 ③；守卫 `tests/ela_markdown_viewer/test_md_cjk_fonts.py::TestProducedGlyphs`
（运行时用 `QRawFont.supportsCharacter` 钉住新标记、并断言渲染产物不含旧标记）。

任意模型输出仍可能带缺字符号：查看器已默认用 `_internal.applyMissingGlyphFonts`
给缺字片段套单族符号字体（Segoe UI Symbol / Cambria Math，只改字体族、不改文本；
`ElaMarkdownViewer.setMissingGlyphFallbackEnabled(False)` 可关），没有候选覆盖的
字符保持原样。`ElaTerminalView` 也已默认接入（增量尾行 / 裁头用水位线；
`setMissingGlyphFallbackEnabled(False)` 可关）；其它 `QTextDocument` 组件可复用该工具。库不做有损替换
（改文本会破坏代码块 / 复制语义），宿主需要替换原文时仍可自行预筛（下游
`probes/` 已有运行时 cmap 查询与「单族全覆盖字体」可行性探针）。

### 2026-10-22 更新：GDI 字体引擎绕过（issue crystalidea/qt6windows7#63）

- `crystalidea/qt6windows7#63`（6.8.4 不读系统 ClearType 设置）确认了 Qt 6.8.4 的 Win7 DirectWrite 路径异常；该 issue 给出的 workaround 是 `-platform windows:nodirectwrite`，即整进程切到 **GDI 字体引擎**。
- 本机 Win10 用 `tools/perf/bench_font_engine.py` 做了 A/B：default `ascii_before/after` 5.1/5.2 ms，`nodirectwrite` 3.9/3.8 ms；两种引擎都**没有**复现「CJK 后 Latin 变慢」（Win10 本来就不复现 #15）。GDI 在本机不更慢。
- 因此这是 #15 目前最可行的**宿主级**绕过：在 Win7 上、`QApplication` 之前设置
  `QT_QPA_PLATFORM=windows:nodirectwrite`（或 `-platform windows:nodirectwrite`），再用
  `tools/perf/bench_font_engine.py` 对比 `ascii_after / ascii_before`。若倍率从 10~40× 回到 ≈1，即可确认并关闭本条；若无效，说明慢路径在 GDI 侧，需要另找 Qt 源补丁。
- 代价：GDI 会改变整进程字体渲染（ClearType / 彩色字体），所以**不进库默认**；库侧可控触发点已全部收口，不替宿主改平台插件。
