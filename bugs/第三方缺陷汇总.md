## #2 ElaMenu：菜单含 checkable 项时，addElaIconAction 的项图标不渲染（被勾选列整列替代）

> 原文出处：`full.md`

**PyQt6 复测（2026-10-16）**：复现——像素判别探针 `probes/recheck_menu_checkable_icon.py`（直接驱动 C++ ElaMenuStyle 的 `drawControl(CE_MenuItem)`，项几何经真实 show 后 actionGeometry 取，画布 `painter.translate(-rect.x(), -rect.y())` 对齐项原点）：非 checkable 分支图标列 145px 墨色、checkable 未勾选图标列 0px（项图标被勾选列整列替代）、勾选时该列画 Check 字形（60px）。源级 ElaMenuStyle.cpp:93 `if (mopt->menuHasCheckableItems)` 分支仍在（C++ 组件 0.13.0 同版）。

**库 / 组件**：PyQt5ElaWidgets C++ ElaMenu / ElaMenuStyle（ElaWidgets/Development/ElaMenuStyle.cpp 的 drawControl(CE_MenuItem)）。

**现象**：只要菜单里存在任意一个 checkable 项，QStyleOptionMenuItem.menuHasCheckableItems 为真，C++ 样式走 if/else 的 checkable 分支：图标列位置统一改画 Check（勾）/ None（空）字形，addElaIconAction(icon, text) 传入的 ElaIconType 图标（action 属性 ElaIconType）与 QIcon 全部不绘制。图标列与勾选列二选一，无法共存。

**复现**（2026-10-12 本机实测，当前安装 pyd）：

1. 源级：ElaMenuStyle::drawControl 中 if (mopt->menuHasCheckableItems) 分支只 drawText(..., mopt->checked ? Check : None)，else 分支才读 action->property("ElaIconType") 圆图标。
2. 行为级（探针 probes/probe_menuitem_style.py）：ElaMenu 两项均 setCheckable(True) + addElaIconAction(Hammer/DiagramProject, ...)，直接驱动 menu.style()（构造时 setStyle 装入的 C++ ElaMenuStyle）的 drawControl(CE_MenuItem, opt, painter, menu)，opt.rect 取 actionGeometry 真实 item 几何：
   - opt.menuHasCheckableItems=True → 只出勾选，无图标；
   - opt.menuHasCheckableItems=False → 正常出图标；
   - （离屏 show() + grab() 截图不可用：offscreen 平台不渲染字体字形，截图全黑，只能走 style 直绘。）

**期望行为**：checkable 项与项图标互不排斥——勾选标记与图标应分列共存（如「图标列 + 勾选列」，或勾选叠加在文本侧），addElaIconAction 的图标在 checkable 菜单里照常渲染。

**项目侧临时规避与移除条件**：无规避（按约定不做绕开，如「状态写进文案 + 换图标」那类变通不采用）。受影响处：宿主应用的 plan/build 双项 checkable 模式菜单（项上分别传 DiagramProject / Hammer 图标——库修复后即生效，当前仅勾选列渲染）；宿主应用托盘「划词助手：开/关」状态项（刻意不传图标，状态写进文案 + 换图标）。库修复（checkable 分支也绘制项图标）后，宿主侧「库缺陷#2」注释可删、模式菜单项图标自然出现；托盘项可评估恢复图标。

## #10 ElaContentDialog / ElaMessageDialog：替换内容区后窗口高度不重新适配，多行正文被裁切

> 原文出处：`full.md`（标题行）、`full (2).md`（正文；末尾截断）

**PyQt6 复测（2026-10-16）**：复现——probes/recheck_messagedialog_height.py 重跑（offscreen 尺寸协商不受离屏渲染限制）：构造后 400×30 → show 后 400×132（内容 sizeHint 145），label 实际高 15 < heightForWidth(350)=26 → 裁切；规避：setMinimumWidth(560)+adjustSize 后 560×145 不裁切；一行短消息与「正文 + ElaLineEdit」形态不受影响——四个场景形态与原记录逐一相同。

**库 / 组件**：PyQt5ElaWidgetTools C++ ElaContentDialog（ElaContentDialog.cpp 构造器 resize(400, height()) + showEvent 不 adjustSize）+ pyqt5_ela_pro ElaDialogBase / ElaMessageDialog（setCentralWidget / Regression 后不改窗口尺寸）。

**现象**：ElaMessageDialog 的 message 在 400px 宽下换行为 ≥2 行时，正文 ElaText（wordWrap）被垂直裁切——每行只露上半截，按钮栏正常。库自带默认内容（「退出/确定要退出程序吗」）是一行短文本、最小高 ≈ sizeHint，所以开箱无感；任何经 setCentralWidget 换入更高内容（换行正文、加输入行等）都会踩到。

**根因**（2026-10-12 探针 probes/recheck_messagedialog_height.py 实测）：C++ 构造器 resize(400, height()) 时 height() 还是默认值 30，窗口被定死 400×30；Python 层随后 setCentralWidget 换内容不重算窗口尺寸；show 时只长到布局最小高 132（内容 sizeHint 为 144），换行 label 分到 15px 而 heightForWidth(350)=25 → 裁切。

**复现**（离屏，`uv run python probes/recheck_messagedialog_height.py`）：

```python
dlg = ElaMessageDialog(
    title="更新技能",
    message="技能 ppt-master 最新版本为 v0.4.0（当前 v0.4.0），将下载并更新到最新版本。",
    parent=host,

dlg.show()  # 窗口 400×132, label 几何 (25,42,350,15), 需要 25 → 裁切
```

一行短消息与「正文 + ElaLineEdit 输入行」形态（_KeyCreateDialog）不受影响（label/输入框最小高 = 需要高，布局撑得开窗口）。

**期望行为**：setCentralWidget / Regression 后窗口按内容 sizeHint 重新适配（如 showEvent 里对「尺寸未经用户设定」的窗口 adjustSize()），多行正文完整显示。

## #10 非主屏最大化时 isFullScreen() 误报 → 标题栏拖拽失效（ElaAppBar NCHITTEST 闸门）

> 原文出处：`full (3).md`（末尾疑似截断）

**PyQt6 复测（2026-10-16）**：复现——probes/probe_fullscreen_state.py：副屏最大化后无边 QWidget isFullScreen=True 且 isMaximized=False（比原记录更重——原记录仅 isFullScreen 误报、isMaximized 仍 True），ElaWindow 副屏 isMaximized=True isFullScreen=True；主屏两者均正确。probe_maximize_discriminate.py：副屏最大化后 maximize 按钮位仍回 HTZOOM（库 NCHITTEST handler 在跑），标题栏 y=12 x 扫描全 HTCLIENT（主屏同扫描为 HTCAPTION）——caption 分支仍被误报中断，副屏最大化后标题栏拖不动。

**库 / 组件**：根因在 Qt 5.15 Win7 平台插件的 fullscreen 状态推断（无 Qt 源码现场，机制为推断）；表现层 PyQt5ElaWidgets C++ ElaAppBar::takeOverNativeEvent 的 WM_NCHITTEST（ElaWidgets/ElaAppBar.cpp ~L644）。

**现象**：窗口（无边框 / 自绘边框）在无任务栏的副屏上最大化后，标题栏（appbar）命中测试整条返回 HTCLIENT（而非 HTCAPTION）→ 最大化状态下从标题栏拖不动窗口（Windows 原生语义本应是「还原 + 拖动」）。主屏（带任务栏）最大化正常。非最大化状态两屏均正常。

**根因链**（2026-10-12 本机实测，Win7 SP1，双 1920×1080 并排，任务栏仅主屏底部；探针 probes/probe_fullscreen_state.py / probes/probe_maximize_drag2.py / probes/probe_maximize_discriminate.py）：

1. QWindow::isFullScreen() 误报：三方对照（最大化后续状态）——原生边框 QWidget 副屏 isFullScreen=False √；Qt::FramelessWindowHint QWidget 副屏 isFullScreen=True；ElaWindow 副屏 isFullScreen=True x；三者主屏均 False √（isMaximized() 两屏正确为 True）。
2. 机制（推断）：主屏底部 40px 任务栏使最大化窗口高 1040 ≠ 屏高 1080；副屏无任务栏，无边框窗最大化后恰好铺满副屏完整几何（(1920,0,1920×1080)）→ 平台插件把「无边框 + 恰好铺满整屏」推断为 fullscreen（Qt 的 showFullScreen 在 Win 上正是这样实现几何的），该推断不区分窗口实际处于 maximized 原生状态。
3. 表现：ElaAppBar.cpp NCHITTEST 的 caption 闸门 if (d->_containsCursorToItem(this) && !window()->isFullScreen()) → 误报的 isFullScreen 直接掐断整条标题栏。判别证据：副屏最大化后标题栏 x 扫描 (y=12) 全 HTCLIENT（主屏同扫描 HTCAPTION），而 maximize 按钮位置仍返回 HTZOOM (=9) ——库 handler 在跑，只有 caption 分支被掐；Qt 侧几何无偏移（appbar mapToGlobal 正确。QCursor::pos() 与 appbar 矩形包含关系实测为真）。

**期望行为**：

- Qt 侧：窗口处于原生 maximized 状态时 isFullScreen() 必须为 False（fullscreen 状态只应反映显式 showFullScreen() 请求）。
- 库侧（表现层）：NCHITTEST caption 闸门改为 !isFullScreen() || isMaximized()（或自行跟踪「用户是否显式请求全屏」）——最大化时标题栏按 Windows 语义应给 HTCAPTION，支持还原 + 拖动。 **（原文片段至此疑似截断，未含「项目侧规避」段）**

## #12 PySide6/Qt6 + C++ ElaPlainTextEdit：终端内容全幅重绘 ~83ms（DirectWrite shaping 无跨 paint 缓存）

> 原文出处：`full (4).md`

**PyQt6 复测（2026-10-16）**：复现——probes/recheck_terminal_repaint.py（真实平台 + WA_DontShowOnScreen，viewport().repaint() 统一口径，1500 行 CJK 日志 680×500）：ElaTerminalView（Consolas + 逐行 char format）全幅重绘 82.7 / 82.8 / 83.3 ms 中位（与原记录 83ms 相差数毫秒）；同内容裸 QPlainTextEdit 3.8~5.5 ms（先经 grab() 采样确认对照在真实渲染——QPlainTextEdit 的 widget.repaint() 只付 0.1ms 是口径差异，须用 viewport().repaint()）。

**库 / 组件**：PyQt6ElaWidgetTools C++ ElaPlainTextEdit（pro ElaTerminalView 的 C++ 底层；终端默认字体 _DEFAULT_FONT_FAMILY="Consolas" 与逐行 char format 来自库 pyqt6_ela_pro/terminal_view.py::_render_line）+ Qt 6.8 / DirectWrite 字体 shaping。

**现象**：全幅重绘（顶层窗口 resize——Windows 顶层 resize 作废整个客户区、滚动、新日志行、切主题，均触发）在真实 1500 行终端内容下实测 ~83ms/次（上屏测量）；同内容裸 QPlainTextEdit 仅 0.2~8ms。成本与总行数无关（~2.7ms/可见行，可见约 30 行）——每次全付的是可见区的 shaping，1500 行终端与 30 行终端重绘同价。

**归因**（2026-10-14 G6/G12/G13 探针，C:\Users\liujie_rdc\.opencode\plan\perf\_probe\；探针的视口/可见行数与活终端不同，绝对值高于活机实测、比率可参考）：

1. C++ ElaPlainTextEdit 默认字体全幅 paint 4.2ms（裸 Qt 0.2~8ms）：库自身样式（borderless、自绘背景）35x；
2. Consolas 等宽 → 175ms（×42）：Consolas 纯 Latin，终端内 CJK 走 DirectWrite 逐字形 fallback，shaping 结果无跨 paint 缓存，每次 paint 对可见区整体重新 shaping；
3. 逐行 char format（_render_line 对每行每个 span 都写 char format，含与默认色相同的 plain 行）→ 262ms：char format 把文本切成更多片段，shaping 单位成倍放大；
4. 活终端（Consolas + 逐行格式 + borderless）实测 83ms（G11 两种配置同星级复现）。

**期望行为**：

- 库侧：ElaPlainTextEdit 的 paint 具备跨 paint 的文本 layout / shaping 缓存（对齐 QTextDocument block 缓存语义），局部内容变化走增量更新；
- terminal_view.py::_render_line 对与默认色相同的 span 不写 char format（减少片段）；
- 默认字体 Consolas 对 CJK 内容不合理（纯 Latin 字形 + 逐字 fallback），建议重新选择默认字体或提供 CJK 友好默认。

**项目侧临时规避与移除条件**：无规避（约定：库 / Qt 问题不绕开、如实报告）。宿主应用另有「首事件钉宽、停手结算」的交互 resize 重排守卫，解决的是重排层成本（Qt6 重排为 Qt5 的 25~30 倍，逐帧 ~180ms）——与本条重绘层相互独立：守卫落地后窗口拖拽仍付 ~83ms/帧的重绘（重排已归零）。库修复 paint 缓存 / 默认字体后本条可关闭。

## #13 pyqt6_ela_pro ElaChatView.setResizeReflowDeferred：内置延迟重排失效（冻结值=新定=不省重排）

> 原文出处：`full (5).md`

**PyQt6 复测（2026-10-16）**：复现——probes/recheck_chat_reflow_deferred.py（40 条 DIAG6 同型短消息、minMessages=10、真实平台 + WA_DontShowOnScreen；子类 resizeEvent 在 super() 之后捕获 _resize_frozen_width / _content.width() 快照，无定时器时序歧义）：680→780 resize 事件时刻冻结值 = 770 = 新内容宽（视口 780 - 10 边距），逐帧重排成本 195.7 ms，与 deferred=off 的 194.4 ms 无差（原记录 ~189ms/帧 同量级）——「停手后一次性重排」仍未生效。库内 view.py::on_view_resized 仍在 super().resizeEvent() 之后读 self._content.width()（布局 pass 已同步拉到新宽）。

**库 / 组件**：pyqt6_ela_pro/chat/view.py ElaChatView（_on_view_resized / _resize_reflow_* 一族）。

**现象**：setResizeReflowDeferred(True, minMessages=N) 开启后，窗口拖拽 / 视图 resize 期间全部消息的逐帧重排成本不变（40 条消息离屏实测 ~189ms/帧，与未启用同量级；上屏口径即宿主窗口拖拽 190260ms/帧）——「停手后一次性重排」设计未生效，重排仍逐帧发生。

**根因**：resizeEvent → _on_view_resized(event.size().width()) 用 self._content.width() 作冻结值，但 Qt6 事件时序下视图的布局 pass 先于其自身 resizeEvent 处理函数（滚动区内容被同步拉到新视口宽），读到冻结值时已是新宽 → setFixedWidth(新宽) = 无 letterbox = 不省重排。DIAG6 探针实测：事件时刻 content=770（新视口宽）、_resize_frozen_width=770。

**复现**：独立 ElaChatView + minMessages 条消息 + setResizeReflowDeferred(True, minMessages=10)，测 resize(w+100,h) + processEvents 成本 = 每次 ~190ms，同时 _resize_frozen_width = 新视口宽。

**期望行为**：冻结值取 resize 前的内容宽度（旧宽）；或在布局 pass 之前就持有内容宽（上一轮结算 / show 时预钉）。

**项目侧临时规避与移除条件**：宿主侧接法 = 交互 resize 重排守卫钉 view._content，on_settle 调库 _sync_content_width 把内容拉回视口宽（widgetResizable 内容只在滚动区自身 resize 时重算），并 setResizeReflowDeferred(False) 禁用库内置延迟（其 120ms 释放循环会清掉守卫钉宽）。库修复后可移除守卫、恢复库 API（setResizeReflowDeferred(True, minMessages=10)）。

## #14 ElaMarkdownViewer：透明 Base 视口（setTransparentTextBase）使文本 paint 成本 ×8——Win7/Qt6 下滚动密集中文文档 112~118ms/帧

> 原文出处：`full (5).md`（开头，截断）、`full (6).md` + `full (7).md`（正文，两文件重叠）

**PyQt6 复测（2026-10-16）**：复现——probes/md_scroll_perf14.py 重跑：P1 完整 viewer（透明 Base 视口）117.4 ms/step、P2 恢复 opaque Base + setAutoFillBackground(True) 14.4（×8.1）、P3 原生 QTextBrowser 同款透明处理 113.2——与原记录 118 / 14.4 / 112 同量级，透明视口仍为主瓶颈。

**库 / 组件**：pyqt6_ela_pro ElaMarkdownViewer（_applyThemeStyle → pyqt6_ela_pro/_styles.py::setTransparentTextBase）：构造/换主题时把内部 _ElaTextBrowser（QTextBrowser 系）的 palette Base 设为 Qt.GlobalColor.transparent 且 viewport().setAutoFillBackground(False)（「等价于 QSS background-color: transparent」，意图是让宿主卡片底色透出）。

**现象**（2026-10-15 本机实测，Win7 SP1 + PySide6 6.8.3 + pyside6-ela-pro 2026.10.14；1000×700 离屏 WA_DontShowOnScreen、程序化滚动 40px/步计时；交叉印证：嵌入本组件的应用在真实窗口（非离屏）下滚动 13K 字符 / 284 行 / 约 234 行内码的密集中文文档同样明显卡顿，与离屏探针 71ms/帧（≈14fps 等效帧率）同星级）：

- 同文档（CJK 纯文本 13K 字符）同宿主层级：viewer 默认（透明 Base 视口）118ms/帧；同一 browser 实例恢复 Base = opaque + setAutoFillBackground(True) 后 14.4ms/帧（×8.2）；
- 原生 QTextBrowser + 同款 setTransparentTextBase 处理 = 112ms/帧（与 viewer 同价）→ 成本不在 viewer 管线 / 钩子 / 接线，就在「透明 Base + 视口不自填充」这一处理本身；
- 对照组（默认 opaque Base）：原生 QTextBrowser 同文档 12~15ms/帧；viewer 文档对象被原生 browser setDocument 共享渲染 = 8ms/帧。

**归因**（探针链 probes/md_scroll_perf.py ~ probes/md_scroll_perf14.py，逐项排除，全部同文档同层级）：

1. 文档内容 / 结构：排除——markdown 全文、纯文本、剥标记版在原生 browser 上均 1245ms；viewer 管线产物（行内码 char format / 显式前景色 / 160% 行高 / 段落距 / 代码表）在原生上逐一复刻均 715ms（probes/md_scroll_perf12.py M2/M4、probes/md_scroll_perf8.py G3）；
2. _ElaTextBrowser 子类 + ElaThemeWidget 父容器：排除——裸 _ElaTextBrowser（含 theme 父）+ 同文档 12ms（probes/md_scroll_perf10.py 12/13、probes/md_scroll_perf9.py H1）；
3. 容器接线（browser/viewport 事件过滤器、valueChanged→_on_view_scrolled、documentSizeChanged→_schedule_layout_refresh、80ms 布局刷新定时器）：排除——全关后 69.7ms 不变（probes/md_scroll_perf13.py N2）；
4. paint 钩子与双 QPainter(viewport()) 结构：排除——类级替换 paintEvent 为原生 QTextBrowser.paintEvent 后 76ms 不变（probes/md_scroll_perf11.py L2）；
5. 决定性（probes/md_scroll_perf14.py）：唯一变量 = 透明 Base + 关自填充。P1 viewer 透明视口 118ms → P2 恢复 opaque 14.4ms；P3 原生 browser 同款透明处理 112ms。
6. 机制（推断，无 Qt 源码现场）：透明背景文本视口走慢速 paint 路径（不透明快路径/滚动 blit 失效、逐帧 alpha 合成叠加），与 #12（Win7 DirectWrite shaping 无跨 paint 缓存）同族——透明背景把每个可见文本行的重绘成本从 ~0.3ms 放大到 ~2.5ms。
7. 注意：上游 2026.10.14 已优化行内码背景绘制（cursorRect 每视觉行一次、共享 pen/brush，替代旧的每标记段一次）——实测该优化在场（行内码钩子总成本 5.3ms → 4.1ms/帧），但它只占全帧成本的 ~6%，不是主瓶颈；主瓶颈是本条的透明视口。

**复现**（一条命令）：`uv run python probes\md_scroll_perf14.py`（P1 透明 118 / P2 opaque 14.4 / P3 原生同款 112；离屏平台，真实平台 WA_DontShowOnScreen 同法。完整排除键见 probes/md_scroll_perf.py、probes/md_scroll_perf12.py、probes/md_scroll_perf13.py）。 **（原文未含「项目侧规避」段）**

## #15 PySide6/Qt6（Win7）：进程内出现过 CJK shaping 后，其后纯 Latin 文本渲染慢 20~40x（app 级 shaping 毒化）

> 原文出处：`full (8).md` + `full (9).md`（开头续接）

**PyQt6 复测（2026-10-16）**：复现——probes/md_scroll_perf5.py 两序各独立进程：cjk_first 68.0 / 238.0 / 127.5 / 14.0 ms/step（viewer+CJK / viewer+ASCII / 原生+ASCII / 原生+CJK），ascii_first 6.2 / 67.4 / 233.3 / 128.5——纯 Latin 从 6.2 放大到 ~233（×38），原生 browser 同样毒化（128），CJK 自身两序恒定 6768。与原记录（71.3/223.7/123.3/14.6 与 6.2/71.4/229.5/127.0）同量级。Qt 6.8.2 未见改善。

**库 / 组件**：PySide6 6.8.3 / Qt 6.8 DirectWrite 字体 shaping（Win7 SP1）。纯 QTextBrowser + setDocument 即复现，与 ela 无关（新建 QTextBrowser / 新建 QTextDocument 实例都无法摆脱 → app 级状态，推断在字体引擎/shaping 缓存层）。

**现象**：同一进程内只要渲染过 CJK 文本，其后一切纯 Latin 文档的滚动 paint 成本放大 2040×；纯 ASCII 文档（13K 字符、约 100 折行）**123127ms/帧**（原生 QTextBrowser，~8fps）；全新进程（无 CJK 历史）同文档 6ms/帧（160fps）。CJK 渲染本身不受历史影响（恒 1415ms/帧原生口径）。两种顺序均复现且数值稳定：

- CJK 先行：viewer+CJK 71.3 → viewer+ASCII 223.7 → 原生新 browser+ASCII 123.3 → 原生+CJK 14.6；
- ASCII 先行：viewer+ASCII 6.2 → viewer+CJK 71.4 → viewer+ASCII（再次）229.5 → 原生+ASCII 127.0。

**复现**（2026-10-15，`uv run python probes/md_scroll_perf5.py cjk_first` 与 `... ascii_first`；离屏 1000×700、40px/步；probes/md_scroll_perf4.py m2~m6 为同型状态矩阵）。

**期望行为**：CJK 与 Latin 的 shaping / 字形缓存相互独立，任一脚本的渲染历史不应劣化另一脚本的后续渲染（至少不跨脚本毒化）。

**项目侧临时规避与移除条件**：无规避（项目约定）。影响面：以 CJK 为主的文档不受显性影响（CJK 自身不劣化，实测原生 15ms/帧含 234 个行内码 token）；受影响的是纯英文 / 纯 Latin 文档——宿主进程只要已渲染过 CJK（如宿主应用自身 UI 文案），其后打开纯 Latin 文档即 20× 变慢。注意与 #14 独立：#15 在原生 browser 上同样存在（123ms），viewer 无关；两者叠加时（viewer + 英文文档 + CJK 历史）实测 230ms/帧。Qt 侧修复（或可解释机制并给缓解）后关闭本条。

## #16 pyqt6_ela_pro combo_box.py：顶层无条件 import pypinyin，包导入即背 ~50 MiB 拼音字典
